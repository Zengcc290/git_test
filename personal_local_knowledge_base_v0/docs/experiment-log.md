# 实验记录：个人本地知识库搜索工具 V1

## 2026-08-10：V0 初版

### 目标

先验证“本地文档 → 可检索文本 → 关键词命中”的最小闭环，不引入聊天机器人、向量数据库或远程服务。

### 环境

- Windows PowerShell
- Python 3.12.4
- 项目解释器：`.venv/Scripts/python.exe`
- 数据库：Python 标准库 `sqlite3` + SQLite FTS5
- PDF 抽取：`pypdf`
- PPTX 抽取：`python-pptx`

| 1 | 对 TXT、Markdown 做 UTF-8 读取、换行统一、空白压缩 | 通过，保留 Markdown 标题文字 |
| 2 | 按空行聚合段落，超长段落按边界切分并保留重叠 | 通过，可配置 `chunk_size` 和 `overlap` |

## 2026-08-11：V1 可管理、可验证的知识库

### 中文搜索实现记录

每个 chunk 在写入 `chunks` 后，先使用 jieba 生成空格分隔的词序列，保存到 `chunk_tokens`，再通过外部内容 FTS5 表 `chunks_fts_jieba` 建立中文倒排索引。查询时先将关键词用同一套分词规则转换成 AND 查询，并使用 FTS5 BM25 排序；没有命中时回退到原始文本 FTS5，中文仍无命中时使用参数化 `LIKE` 兜底。V1 的 `--type` 和 `--path` 过滤条件会同时作用于这三条搜索路径。

### 当前结论

V0 已经满足本地文档搜索引擎的最小功能闭环，适合个人少量文档的实验和后续迭代。当前项目保留正式运行代码、命令行验证记录和与正式代码同步的 tests 目录。

索引链路现在采用“固定大小读取/逐页抽取 → 流式清洗 → 流式分段 → SQLite 批量迭代写入”，哈希计算也按固定大小读取。这样大 TXT/Markdown 不会因为 `read_bytes()`、全文清洗或 `list(chunks)` 同时占用大量内存。

### 已知限制

1. PDF 目前只抽取文本层，扫描版 PDF 需要 OCR，暂未支持。
2. PPTX 暂不抽取图片、图表内部文字和演讲者备注。
3. FTS5 的 `unicode61` 适合英文及空格分词文本；中文连续词在无 FTS5 命中时使用参数化 `LIKE` 兜底，排序能力有限。
4. 搜索使用关键词 AND 匹配，不支持自然语言理解、同义词和语义检索。
5. `check-db` 当前只发现问题并输出诊断，不自动修复；自动修复计划放到 V2。
6. `prune` 只清理源文件已经不存在的记录，不会自动识别源文件移动或重命名。
7. JSON 采用单条记录解析，单条记录仍需要能够放入内存；默认 512 MiB 文件上限可通过 CLI 显式设置为 0 关闭。
